## 1. 审计的修正：陷阱 (2) 的归因 ✅ 成立，已采纳

**审计说**：

> 我查了分配逻辑：`seq` 是全局递增的流水号，起点是 1，但被所有条目共享——
> 用户消息占 1，assistant 回复占 2，你的第一次 `AppendEntry` 就落在 3。
> 所以：「从 3 起步」是那次探测的具体结果，不是固定语义。

`next_sequence() = sequence + 1`（`index.rs:66`）——**确实是跨条目共享的全局流水号**。

**审计指出的风险完全成立**：我原来的表述「seq 从 3 起步」会诱导后来者硬编码 `afterSeq: 2`。

**已改**：

> **后果**：**绝不能硬编码 `afterSeq`**。必须**先读一遍拿到最大 seq**，再增量查。

## 2. 审计的探测 1：NavigateTree 切 leaf 后的可见性 ✅ 实测

**审计的推测**：

> 写到当前 leaf，那么切到别的 leaf 后，之前的 Task 就**看不见了**。

**成立，而且比它说的更彻底。**

### 2.1 实测（rpc 模式，同一会话内）

```
写 5 条 custom entry（seq 3~7）后：
  before-nav:  count=5  seqs=[3,4,5,6,7]

NavigateTree 到最早的 message entry：
  NAV: outcome=completed，leaf 已改变
  after-nav: count=0        ← custom entry 全部不可见
```

### 2.2 途中踩到的一个坑（差点得出错误结论）

第一轮测出「先读一次再导航，count 反而是 5」，与预期相反。
我怀疑是**读的副作用**，于是做了对照实验：

```
pre_read=False → after-nav count=0
pre_read=True  → after-nav count=5
```

**根因**：**导航是幂等的**。已在目标 leaf 时再次导航，返回**同一个 `runId`**、
`outcome=completed`，不重复执行。所以「先读一次」的那组，其实第一次导航已经成功了，
第二次是 no-op——而读取发生在导航**之前**，读到的是旧 leaf。

我另做了一组验证（同一进程内连续两次导航）：

```
NAV1: runId=6521..., outcome=completed
NAV2 (在一次 read 之后): runId=6521..., outcome=completed   ← 同一个 runId
```

**确认是幂等**。真实结论只有一个：**导航后 custom entry 不可见（count=0）**。

### 2.3 结论的性质

**Task 状态是「分支绑定」的，不是「会话绑定」。**

| 影响 | 说明 |
| --- | --- |
| Task 状态**不能**跨分支 | rewind 后 Task「消失」——**但数据没丢**，切回去还能读到 |
| 落地策略 | 要么接受「rewind 后看不到 Task」的语义，要么 Task 状态绑定到它所属的分支 |
| **推高方案 B 的价值** | 若用户频繁 rewind 探索，Task 视图会反复消失——这比「换 session」**更常见** |

**已写入 §2 G1 的「分支语义」小节 + 风险表第 23 条。**

### 2.4 顺带实测：compact 不影响 custom entry

```
before-compact: count=5 seqs=[3,4,5,6,7]
COMPACT: {"accepted": true}
after-compact:  count=5 seqs=[3,4,5,6,7]     ← 完全不变
```

**custom entry 不受 compaction 影响**——这是好消息（compaction 会重写 branch，
本来担心它会丢 Task 状态）。

## 3. 审计的探测 2：规模测试 ✅ 实测，**担忧被推翻**

**审计的担心**：

> `AppendEntry` 的语义是每次状态变化 append 一条完整数据……
> Task t1 状态变化 50 次 → 50 条 custom entry……而 `GetSessionBranch` 读回时
> 无 `afterSeq` → 读整个 branch 的所有条目
> **如果 300 条就慢，A' 只适合「少量长任务」**

### 3.1 实测结果

| 操作 | 实测耗时 |
| --- | --- |
| append 300 条（**全部写入**） | **5.1 ms** |
| 读回全部 300 条（无 `afterSeq`） | **1.36 ms** |
| 读回全部 300 条 + `limit:10` | **0.11 ms** |
| 增量读（`afterSeq: <max>`） | **0.04 ms** |

**结论：A' 完全撑得住高频状态更新。**

### 3.2 这个结果**改变了设计**（审计会喜欢这一点）

我原计划（审计的 §8.2 第 1 条）倾向「只在状态**实质变化**时 append」，
或者「内存驻留 current state，只在关键节点落盘」。

**实测后这两个复杂度都不需要**：

> **这个结果改变了设计**：不需要「内存驻留 current state，只在关键节点落盘」
> 的复杂策略。**每次状态变化都 append** 是可以接受的——简单，且天然有历史。

**留下的限制**：Task 数量级到**千**级时才需重测；那时读全部约 5ms 量级，仍可接受。
真正的问题会变成 session 文件**体积**，不是延迟。
